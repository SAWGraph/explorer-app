1. **Fixed: A Region on Aquifers Let In Aquifers From the Next County** (2026-11-10)

    **Component**: `engine/entities/aquifers.ts`, `subdivisionRegionCheck` in `engine/entities/types.ts`

    **Symptom**: Issue #144. "Aquifers in Hancock County" listed 197 aquifers, and 16 of them lie in Washington, Waldo and Penobscot. In Sagadahoc, 15 of its 25 aquifers were from other counties.

    **Root cause**: The region pick checked only the S2 cell. A cell that crosses the county line touches the county, so every aquifer in it passed. Wells got their own check in #96; aquifers had none.

    **Fix**: An aquifer now counts in a region when one of its county subdivisions (towns) rolls up to it. Any overlap counts: an aquifer that crosses the county line belongs to both counties, since its links are within, overlaps and contains alike. Wells and aquifers share the check. Because the check joins an aquifer to each of its towns, an aquifers side with a region is collapsed to one row per aquifer and cell before the join, as a filtered samples side already is (#82).

    **Measured**: on federation, 2026-11-10, all 118 Maine and Illinois counties. The cell check let in 635 of 10,432 county and aquifer pairs (6.1%), in 109 counties; the new check dropped no aquifer the cell check kept. Traces got faster: Hancock "samples within 10 km downstream of aquifers" went from 34s to 6s, Penobscot "aquifers within 10 km downstream of facilities" from 32s to 4s. Report: https://app.superset.sh/page/aquifer-county-filter-6hwnbk

    **Unchanged**: every wells query and every question without an aquifers region (only aquifer shapes moved in the recorded SPARQL), the result cache (no cached question has an aquifers region, so `DATA_VERSION` stays).

    **Files touched**: `engine/entities/aquifers.ts`, `engine/entities/types.ts`, `engine/entities/wells.ts`, `engine/templates/fusedQueries.ts`, `engine/tests/aquiferRegion.test.ts` (new), `engine/tests/__snapshots__/query-shapes.txt`, `docs/DEBUGGING.md`, `GLOSSARY.md`

    **Prevention**: `engine/tests/aquiferRegion.test.ts` checks that a region on aquifers carries the check near and in traces, on either block, and inside the collapsed side; with `LIVE_SPARQL=1` it also checks the Hancock (181) and Sagadahoc (10) counts.

2. **Shared Links Show a Preview Card, and the Tab Shows the Explorer Logo** (2026-11-10)

    **Component**: `index.html`, `public/`

    **Symptom**: Issue #148. A link to explorer.sawgraph.com on LinkedIn, Slack or X showed a blank placeholder card. The browser tab showed the Vite logo and the title "SAWGraph Query Editor".

    **Root cause**: Crawlers read Open Graph tags from the raw HTML and do not run JavaScript, and `index.html` had none. A missing image does not fail loudly: the SPA fallback (`/* /index.html 200`) answers any missing file with the page itself and a 200.

    **Change**: `index.html` carries a description, Open Graph tags and `twitter:card` (`summary_large_image`), pointing at `public/og-image.png`, a 1200x630 image of the full logo on white. The tab title reads "SAWGraph Explorer" and the icon is `public/favicon.png`, the logo mark on a transparent background. Both images are cut from the header logo. The preview image stays opaque because the navy wordmark disappears on dark-mode cards. There is no `og:url`: set to the root, it would make every shared `/q/` link preview as the homepage.

    **Unchanged**: every shared link gets the same card; a card per question would need server-side rendering. LinkedIn caches the old card until the URL is re-scraped in its Post Inspector.

    **Files touched**: `index.html`, `public/og-image.png` (new), `public/favicon.png` (new), `public/vite.svg` (removed), `ui/tests/linkPreview.test.ts` (new)

    **Prevention**: `ui/tests/linkPreview.test.ts` checks that the preview image and tab icon point at PNGs that exist in `public/`, that the image is 1200x630 as declared, and that there is no `og:url`.

3. **Fixed: Popup Links Only Open http and https IRIs** (2026-11-11)

    **Component**: `ui/components/Map/MapPopup.tsx`, `ui/utils/safeHref.ts`

    **Symptom**: Issue #155. A published view replays the result its publisher uploaded, and the API checks only its size. The stream "Flowline" and sample "Sample Point URI" popup links used an IRI from that result as their `href`, so a `data:`, `ftp:`, `file:` or relative value rendered as a working link.

    **Root cause**: No check between the stored result and the link. A scheme check alone would not have been enough: `wrapUri` does not escape `>`, so the sample point id `https://evil.example/x> <real sample point IRI>` still gets the real point's rows (25 rows, HTTP 200 on federation) and the popup opens in full with a link to `evil.example`.

    **Change**: `safeHref` passes an IRI only when it is `http` or `https` and holds none of the characters SPARQL forbids in an IRI (control and space, `< > " { } | ^` backtick, backslash). The Sample Point URI, Sample URI and Flowline links go through it; a refused value shows as the same text with no link. The FRS and Illinois well links are unchanged.

    **Unchanged**: no real link is lost. Across the live graph the check refuses none of 20,345 sample points, 108,612 samples or 434,501 flowlines, and none of the 34,005 IRIs in the 8 cached dashboard results. `wrapUri` still lets result data rewrite the popup's detail query; that is a separate issue.

    **Files touched**: `ui/utils/safeHref.ts` (new), `ui/components/Map/MapPopup.tsx`, `ui/tests/popupLinks.test.tsx` (new), `docs/DEBUGGING.md`

    **Prevention**: `ui/tests/popupLinks.test.tsx` covers `safeHref`, the stream and sample popups with real and unsafe ids, and a rule test that no popup type links anything `safeHref` refuses (16 of 62 cases fail without the fix).
