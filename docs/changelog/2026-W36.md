1. **Document the Dropdown Discovery Queries in a GitHub Wiki** (2026-09-02)
   Nothing explained what any individual SPARQL query asks for. `SCHEMA.md` lists predicates and `docs/queries/` walks through five complete example questions, but the discovery queries behind the filter dropdowns were undocumented, so an empty dropdown had no page to read. Added nine pages under `docs/wiki/`: an index covering every filter control, and one page each for Substance, Material, Industry, Industry counts and County. Each page states what the control does, gives the SPARQL with a line-by-line plain-English reading, links every hook, builder, endpoint and fallback back to `main`, and ends with a list of what specific wrong-looking results mean. Screenshots are referenced but not yet supplied, so those links render broken on purpose.

   The wiki source lives in the repo rather than in the wiki UI, so a docs change goes through the same PR as the query change it describes. `.github/workflows/wiki-sync.yml` copies the pages across on every push to `main`. Pages are flat files named for their eventual page title, since GitHub wikis have no folders.

   Every documented query was run against the live endpoint before being written down, which surfaced the three findings below.

   *Files:* `docs/wiki/` (new, 9 pages), `.github/workflows/wiki-sync.yml`, `docs/CONVENTIONS.md`, `CLAUDE.md`

2. **Found: Unfiltered Substance Dropdown Always Falls Back** (2026-09-02)
   With no region selected, `buildDiscoverSubstancesQuery()` returns zero rows, so the dropdown silently shows the seven hardcoded PFAS entries in `FALLBACK_SUBSTANCES`. The query requires `dcterms:alternative` for the label, and the `sawgraph` endpoint has zero triples using that predicate; substances there carry `rdfs:label`. This corrects last week's claim that all discovery queries return live data after the host migration. Not yet fixed. The fix is to accept `rdfs:label` in the label pattern.

   **Correction (2026-09-08):** this entry originally said `dcterms:alternative` "exists only on `federation`, which is why the region-scoped variant works and returns 71 substances for Maine", and proposed pointing the no-region query at `federation` as one possible fix. That was wrong. `dcterms:alternative` has zero triples on substances on `federation` too, so the region-scoped variant was returning zero rows as well and the whole dropdown was broken, not just the unfiltered one. The proposed `federation` fix would not have worked. See week 37.

   *Files:* documented in `docs/wiki/Dropdowns Substance.md`

3. **Found: Material Type URIs Differ Between Endpoints** (2026-09-02)
   `sawgraph` names groundwater `me-egad#sampleMaterialType.GW`; `federation` names the same material `me-egad-data#sampleMaterialType.GW`. Since the Material dropdown switches endpoints once a state is picked, and selections are stored as URIs, a material chosen before selecting a region stops matching after. Not yet fixed. Documented as a known quirk.

   *Files:* documented in `docs/wiki/Dropdowns Material.md`

4. **Found: Industry Tree Shape Is Inferred, Not Queried** (2026-09-02)
   The `?groupCode` column returned by `buildDiscoverIndustriesQuery()` is the two-digit NAICS sector, not the four-digit parent the `FALLBACK_NAICS` shape implies. The actual hierarchy is built client-side in `useNaicsTree.ts` by trimming code strings one character at a time until a matching ancestor is found, so a missing intermediate code makes its children attach further up and the tree ends up flatter than real NAICS. Working as designed, but not obvious from either the query or the fallback constant, so it is now written down.

   *Files:* documented in `docs/wiki/Dropdowns Industry.md`
