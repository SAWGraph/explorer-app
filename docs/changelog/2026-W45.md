# Changelog, Week 45, 2026 (Nov 2 to Nov 8)

1. **Fixed: A Region on Wells Let In Wells From the Next County** (2026-11-05)

    **Component**: `regionClause` in `engine/templates/fusedQueries.ts`

    **Symptom**: Issue #96, reported by David Kedrowski. "Wells near surface water bodies in Hancock County, ME" at 0 cells away returned 2,264 wells. 35 of them sit outside Hancock: 25 in Penobscot, 6 in Waldo, 4 in Washington. Putting the region on the water bodies, the wells or both gave the same answer.

    **Root cause**: The region clause only required the S2 cell to touch the region. A cell that crosses the county line touches the county, so every well in it passed.

    **Fix**: When a wells block has a region, the well must also link to a county subdivision that rolls up to the region (`kwg-ont:administrativePartOf+`, so a state region works too). The cell clause stays because it narrows the search first. Discovery, the chunk probe and well hydration share the clause, so all three apply it. A well with no subdivision link drops out of a region answer (1,092 of 379,496 Illinois wells, none in Hancock). Measured on federation, region on wells or on both: 2,264 to 2,229 wells at 0 cells, 5,222 to 5,125 at 1 cell.

    **Unchanged**: every other block type emits byte-identical SPARQL. Water bodies have no links to administrative regions, so a region on water bodies is still checked by cell only.

    **After deploy**: the result cache key describes the question, not the engine, so cached wells answers with a region keep serving the wider result. Purge them.

    **Files touched**: `engine/templates/fusedQueries.ts`, `engine/tests/wellRegion.test.ts` (new), `engine/tests/__snapshots__/query-shapes.txt`

    **Prevention**: `engine/tests/wellRegion.test.ts` checks the well-level clause on near, downstream and upstream, bounded and not, in the chunk probe and in well hydration, and its absence elsewhere. With `LIVE_SPARQL=1` it also checks the Hancock counts on federation and that no returned well lacks a Hancock subdivision link.

2. **Near Distances Read as "Within at Most X Miles"** (2026-11-05)

    **Component**: `RelationshipSelector`, `questionGenerator`

    **Symptom**: Issue #76. At 0 miles the Analysis Question said only "near", so a reader could not tell which distance was picked. The other options, "~1 mile" to "~4 miles", understated how far apart a match can be.

    **Root cause**: The labels showed the hop count, the number of steps to a touching S2 cell, instead of the distance it allows. A level 13 S2 cell is about 1 mile corner to corner, so N hops keeps every match within N+1 miles. The sentence also had a special case for 0 hops that dropped the distance.

    **Change**: The relationship stays "Near", and its distances read "within at most 1 mile of" to "within at most 5 miles of", as agreed on #76. The question follows, for example "What wells in Maine are within at most 2 miles of Solid Waste Landfill, National Security facilities?". Measured cell diagonals run 0.87 to 1.11 miles across Maine, Indiana, California, Texas and Florida, so the bound can be off by up to about 11% outside Maine and 5% inside it.

    **Unchanged**: the query, the hop values, the cache key, saved questions, prebuilt titles and tags.

    **Files touched**: `ui/components/QueryEditor/RelationshipSelector.tsx`, `engine/questionGenerator.ts`, `engine/tests/questions/filters.ts`, `engine/tests/__snapshots__/question-text.txt`, `docs/wiki/Dropdowns.md`

    **Prevention**: `engine/tests/__snapshots__/question-text.txt` records the sentence for every hop value, so a wording change shows up as a snapshot diff.

3. **Fixed: A Refused Wells Step Split Into Identical Queries** (2026-11-05)

    **Component**: `hydrateStep` in `engine/planner.ts`

    **Symptom**: When the server refused the wells details step (timeout, out of memory), the step kept splitting and resending until the 300s step budget ran out, then failed. Issue #82's wells step spent 533s this way.

    **Root cause**: Wells details re-derive the well set server-side (`buildFusedWellQuery`) and ignore the scope they are given, but the step kept the by-IRI `divide`. Each refusal halved the IRI list into slices that all built the byte-identical query.

    **Fix**: Wells get no `divide`, so a refused wells step fails on its first refusal with its error. Splitting comes back when wells load by IRI (engine redesign, Phase 2). Cherry-picked from `fc955d6` on the closed #94 branch.

    **Unchanged**: every query's SPARQL, and every other entity type. Questions that succeed are unaffected.

    **Files touched**: `engine/planner.ts`, `engine/tests/stepDivide.test.ts` (new), `docs/DEBUGGING.md`

    **Prevention**: `engine/tests/stepDivide.test.ts` checks all 108 question shapes: every divisible step builds a different query for each slice, and no slice re-sends the undivided query.

4. **Map Decoration Loads Alongside the Answer** (2026-11-06)

    **Component**: `executePipeline` in `engine/executor.ts`, step waits in `engine/planner.ts`

    **Before**: Every step ran in plan order. The region boundaries (they need only the state) waited for both discovery steps and both details steps, and the stream lines waited for details they never read.

    **Now**: Each step names the steps it waits for (`after`), and the executor starts every step whose wait is over. Boundaries start with the run; stream lines start once both sides are found, while the details load. The main steps still run one at a time. A run that ends early stops what is still loading and reports it skipped. The edit modal's timeline numbers steps by their place in the plan.

    **Measured**: live on the 8 dashboard questions, decoration time left after the last main step was 7.8s and 26.2s before, 0.7s and 2.3s after (Cumberland upstream), and 2.0s and 14.7s before, 0s after (Indiana downstream). Boundaries are 0.3s to 0.7s on a warm server cache, so their saving shows only when cold.

    **Unchanged**: every query's SPARQL, the result shape and the cache key. Health-check: 8 of 8 working, every row count the same.

    **Files touched**: `engine/executor.ts`, `engine/planner.ts`, `ui/components/Pipeline/PipelineTimeline.tsx`, `engine/tests/stepWaits.test.ts` (new), `ui/tests/pipelineTimeline.test.tsx` (new), `engine/tests/executor.test.ts`, `docs/DEBUGGING.md`, `docs/ARCHITECTURE.md`

    **Prevention**: `engine/tests/stepWaits.test.ts` checks every shape's waits; the "decoration alongside the main steps" tests in `engine/tests/executor.test.ts` fail if decoration waits its turn again.

5. **Both Sides Are Counted Before a Question Runs** (2026-11-06)

    **Component**: count steps in `engine/planner.ts` (`COUNT_TARGET`, `COUNT_ANCHOR`), `buildEntityCountQuery` in `engine/templates/fusedQueries.ts`, `engine/executor.ts`, `engine/errors.ts`, `chooseAxis` in `engine/slicing.ts`

    **Before**: The engine did not know how big either side was. A block that matched nothing still ran discovery and ended with "No results found for this query". The advice after a refusal guessed from whether a filter was set, and counted the default non-detect tick as one. Splitting a refused query probed both sides, then threw a full probe away.

    **Now**: Every run counts both sides first, together; discovery waits for both. A side at 0 ends the run before any discovery query: "No wells match the first block, so the question has no answer. Try a wider region or fewer filters." A refused question's message gives both counts and names the bigger block ("The first block matches 4,528 samples, the second 459,877 facilities"). Splitting skips a probe the count says would come back full; the order (anchor first) is unchanged. A count that fails or takes over 10s is dropped and the run goes on, with chunking on or off. Run option `countSides: false` turns the counts off.

    **Measured**: live on 2026-11-06, 57 of 58 cold counts took 1.1s or less; inside dashboard runs the counts took 0.4s to 0.8s, alongside the boundaries. Wells in Marion County, Indiana near landfills now ends empty in 0.4s on one request.

    **Unchanged**: every discovery, details and decoration query (the golden snapshot only gained the count queries), the result cache. Health-check: 8 of 8 working, every row count the same.

    **Files touched**: `engine/planner.ts`, `engine/executor.ts`, `engine/errors.ts`, `engine/slicing.ts`, `engine/run.ts`, `engine/templates/fusedQueries.ts`, `engine/scripts/query-sweep.mts`, `engine/tests/slicing.test.ts` (new), `engine/tests/executor.test.ts`, `engine/tests/errors.test.ts`, `engine/tests/stepWaits.test.ts`, `docs/DEBUGGING.md`, `docs/ARCHITECTURE.md`

    **Prevention**: "counting both sides first" in `engine/tests/executor.test.ts` and the count advice tests in `engine/tests/errors.test.ts`.

6. **Fixed: Filtered Sample Questions Joined One Row per Measurement** (2026-11-06)

    **Component**: `fansOut` and `bindInCell` in `engine/entities/` (samples, facilities), `collapsedSide` and `buildFusedWellQuery` in `engine/templates/fusedQueries.ts`

    **Symptom**: Questions with a sample filter took minutes or failed. Issue #82's question (samples above 4 ng/L in Penobscot and Knox near wells in the same counties) failed after 626s, and "wells near samples above 4 ng/L" in the same counties failed every run.

    **Root cause**: A side's bind repeated each entity once per value of a multi-valued field, and the repeats only collapsed at the final `DISTINCT`. Maine samples at 4 ng/L or more: 78,369 rows for 2,207 sample points. Facilities with no code filter or a prefix code: about 2 rows per facility. The wells step also joined every measurement on a samples side and attached its columns to the whole fan-out.

    **Fix**: A side that fans out is collapsed to one row per entity and cell (`SELECT DISTINCT`, with its region and pin inside) before it meets the other side. Facilities collapse only under a prefix code or no code filter; a full 6-digit code matches itself only, and collapsing it tripled the Maine wells questions' discovery time. The wells step uses the trimmed bind and collapses its join before the well columns attach. Discovery counts only sample points the map can draw: a location, and a filtered match that names a chemical (not a sum row such as SUM_PFOA_PFOS).

    **Measured**: live, best of 2, before and after: #82's question 41.7s to 23.7s; wells near samples above 4 ng/L, failed to 52.6s; samples above 4 ng/L with no region near wells in Somerset 65.4s to 8.7s; facilities upstream of PFOS samples in York 38.9s to 4.2s; dashboard Cumberland 49.9s to 5.8s, Cook 11.1s to 3.9s, the two Maine wells questions 22.2s to 11.4s and 25.6s to 16.4s.

    **Unchanged**: the samples the map draws, and every dashboard row count (health-check: 8 of 8 working). Discovery drops what sat only next to undrawable points: #82 finds 201 sample points instead of 207 and 2,597 wells instead of 2,614.

    **Not fixed**: water bodies downstream of wells in Maine still answers slowly or fails (948s, partial); wells by IRI (engine redesign, Phase 2) is the fix.

    **Files touched**: `engine/entities/*.ts`, `engine/templates/fusedQueries.ts`, `engine/tests/oneRowPerCell.test.ts` (new), `engine/tests/queryJoins.test.ts`, `engine/tests/questions/critical.ts`, `docs/DEBUGGING.md`, `docs/ARCHITECTURE.md`

    **Prevention**: `engine/tests/oneRowPerCell.test.ts` checks every question shape: each side that fans out is collapsed with its region inside, a 6-digit facilities side is not, and the wells step reads no measurement.

7. **Fixed: A Facility Showed One Industry Code, and a Leftover Filter Slot Moved the Trace** (2026-11-06)

    **Component**: `transformFacilitiesToFeatures` in `engine/shape.ts`, the facility popup and tooltip, `ownFilterSet` and `filterSlot` in `engine/entities/`, `ownSlotOnly` in `engine/question.ts`, `engine/cacheKey.ts`

    **Symptom**: A facility's popup and tooltip named one industry code when it had several, and its marker colour came from whichever code the server sent first. Separately, which side a trace started from could depend on a filter slot the block does not use.

    **Root cause**: The details step returns one row per matching code, and the map kept the first row per facility. The filter rule read the first slot it found, whatever the block's type, and counted a label map as a filter.

    **Fix**: One feature per facility with every matching code, sorted; the lowest code colours the marker, the popup lists each code on its own line and the tooltip lists the names. Each entity module reads only its own filter slot and only fields a query reads; normalise and the cache key drop the other slots.

    **Measured**: live on the dashboard, 405 of Indiana's 415 facilities have 2 or more matching codes, 264 of Cook's 402 and 81 of Cumberland's 140 (up to 7). No marker changes colour group.

    **Unchanged**: every dashboard and golden question's SPARQL (the snapshot did not move); health-check 8 of 8 working, every row count the same.

    **Files touched**: `engine/shape.ts`, `engine/types/map.ts`, `ui/components/Map/MapPopup.tsx`, `ui/components/Map/FacilityLayer.tsx`, `engine/entities/*.ts`, `engine/question.ts`, `engine/cacheKey.ts`, `engine/tests/filterSlots.test.ts` (new), `engine/tests/facilityFeatures.test.ts` (new), `ui/tests/facilityPopup.test.tsx` (new), `docs/DEBUGGING.md`

    **Prevention**: `engine/tests/filterSlots.test.ts` checks, for all 108 shapes with and without each block's own filter, that leftover slots send the same SPARQL as the clean question.

8. **A Run Answers by Block** (2026-11-06)

    **Component**: `PipelineSuccess` in `engine/executor.ts`, `engine/wire.ts`, `useMapLayers`, the result cache client, the health-check and thumbnail scripts

    **Before**: A run's result was keyed by pipeline step (`FIND_TARGET_ENTITIES`, `GET_ANCHOR_DETAILS`, ...). Which block is the target flips for upstream, so block A sat under a different key for a third of the questions.

    **Now**: A run returns `blockA`, `blockC` and `decoration` (`boundaries`, `streamLines`), with `partial`, `queries` and `counts`. The result cache stores the same shape (`WIRE_VERSION` w3) and still reads a result stored by step, so published views keep working. The health-check records the same four counts, worked out from the blocks.

    **After deploying**: every cached dashboard question runs live once until `npm run warm-cache` runs for that environment.

    **Measured**: the 8 dashboard results cached on the development API, stored by step, all read through the new reader with upstream questions on the right blocks. Health-check: 8 of 8 working.

    **Files touched**: `engine/executor.ts`, `engine/wire.ts`, `engine/cacheKey.ts`, `ui/hooks/useMapLayers.ts`, `ui/api/resultCacheClient.ts`, `ui/components/Layout/PublishedView.tsx`, `engine/scripts/health-check.mts`, `ui/scripts/build-thumbnails.mts`, `ui/tests/mapLayers.test.ts` (new), `engine/tests/wire.test.ts`, `docs/ARCHITECTURE.md`, `docs/DEBUGGING.md`

9. **A Failed Run Says What Failed, in Parts** (2026-11-06)

    **Component**: `Failure`, `failureOf`, `failureDetail` and `unexpectedFailure` in `engine/errors.ts`, `engine/executor.ts`, `PipelineStep.block` in `engine/planner.ts`, the edit modal

    **Before**: A failed run carried a log line ("Error at step: ...") and the raw error. The edit modal wrote its own "Error:" label over that log line, so a failed Apply read differently from the progress strip.

    **Now**: A failed run carries a `failure`: its code (the classifier's names, as the query-sweep CSVs record them), the step, the block it was working on, the failed and skipped slices, the HTTP status and the server's text. The edit modal shows the progress strip's sentence, then one line such as "Step 3 of 8, finding facilities downstream of facilities (block A): timeout", then the server's text. The sentence is now read from the failure's code, not the error object's class.

    **Measured**: live, facilities downstream of facilities in Maine with chunking off failed with code timeout at step 3 of 8, block A, and the message gave both block counts.

    **Unchanged**: every query and every successful run. Health-check: 8 of 8 working, every row count the same.

    **Files touched**: `engine/errors.ts`, `engine/executor.ts`, `engine/planner.ts`, `ui/components/QueryEditor/EditModal.tsx`, `ui/hooks/useQueryPipeline.ts`, `engine/tests/executor.test.ts`, `engine/tests/errors.test.ts`, `ui/tests/editModalFlows.test.tsx`, `docs/DEBUGGING.md`

    **Prevention**: "what a failure carries" in `engine/tests/executor.test.ts`, and test 1d in `ui/tests/editModalFlows.test.tsx` (the modal shows the sentence, the detail line and the server's text, not the log line).
